# Lens Vault 剩余阶段开发规划

- 更新日期：2026-09-17。
- 文档状态：后续开发规划，尚未实施的内容不代表当前应用已经支持。
- 面向读者：Flutter、Android 开发人员及功能验收人员。
- 目标：在现有 Phase 1 MVP 上，分阶段完成专业录像、拍摄预设和本地文件工具。
- 平台范围：Android，沿用当前最低 API 24；不扩展 iOS、Web 或桌面端。
- 文档性质：实施说明与任务参考；不替代设备能力探测、接口核验和真机测试。

## 1. 当前基线与范围

### 1.1 已完成的 MVP

| 领域 | 当前实现 | 后续需要保持的行为 |
| --- | --- | --- |
| 技术架构 | Flutter UI、GetX、Drift、Kotlin 平台桥接 | 沿用功能模块，不重新搭建项目 |
| 文件访问 | 用户选择 SAF 根目录，保留授权，读取目录真实内容 | 管理已有文件，不仅显示本应用录制的视频 |
| 目录管理 | 多级导航、新建、文件夹改名、文件与目录删除 | 根目录保护；递归删除前显示影响数量 |
| 排序 | 名称、修改时间、文件大小，升序与降序 | 文件夹优先，未知元数据在末尾；目录大小不伪装成已计算值 |
| 视频录制 | 指定目录录制、音频开关、前后镜头、设备范围内连续变焦 | 不硬编码可用倍率；麦克风拒绝时可切静音 |
| 录制规格 | 请求 1080p / 30 FPS，初始化失败时尝试后备配置 | 请求目标不等于实际输出，不以目标标签冒充实际规格 |
| 保存恢复 | 私有暂存、SAF 提交、持久待保存任务、重试与明确放弃 | 保存失败保留可用视频；停止失败与提交失败分别处理 |
| 生命周期 | 进入后台停止并保存，离页前处理进行中的录像 | 不在后台继续录像，不静默丢弃尚未持久登记的源文件 |
| 播放 | 应用内通过内容 URI 播放，展示时长、尺寸和大小 | 播放不依赖把 SAF URI 转成普通文件路径 |
| 本地数据 | 数据库 schema v2：设置、创建时间元数据、待保存录像 | 视频内容不存数据库，不用数据库替代 SAF 目录树 |

当前保护策略：同一根目录存在待保存录像时，暂时阻止其中的文件夹改名和删除。后续批量移动、改名不得绕过该策略；放宽保护前必须先实现任务目标的可靠迁移。

### 1.2 已有验证与验证缺口

上一轮交付记录为：29 项 Flutter 测试、Kotlin 单元测试、静态分析和调试 APK 构建通过。模拟器已验证目录授权、创建、改名、删除确认、指定目录录制、播放、静音及后台停止保存；静音文件经音轨检查没有音频流。

上述结果是 Phase 1 的历史基线，本次文档整理没有重新运行应用测试。模拟器中曾出现请求 1080p、实际输出较低尺寸的情况，因此后续必须分别记录请求值、会话反馈值和成品文件值。

开始扩展前补齐以下验证，结果进入对应里程碑的验收记录：

- 真机相机能力、前后镜头差异、麦克风与相机权限拒绝后恢复。
- SD 卡读写、拔出与重插、只读提供方、目录授权撤销和外部改名。
- 存储不足、停止失败、复制中断、进程终止后的待保存任务处理。
- 长时间录像、设备温度变化和实际成品规格；不把模拟器结果推广到全部设备。
- 保存日志与临时文件清理，尤其是失败后可能遗留的部分目标文件。

不得承诺恢复被系统终止前尚未生成完整成品的录像。恢复能力以已经取得、可读取且已登记的视频源为边界。

### 1.3 全阶段约束

1. 优先复用项目已有依赖和接口。当前声明包含 `camera: ^0.12.1`、`video_player: ^2.14.0`、GetX 和 Drift；声明范围不等于依赖实际解析版本，也不保证所有底层能力都已暴露。
2. 任何相机选项都要通过当前镜头、当前录制组合的能力校验，不能把各参数的独立支持列表随意组合。
3. `content://` URI 与 `documentId` 均是不透明标识，不自行解析为文件路径，也不通过字符串前缀判断目录祖先关系。
4. 默认不覆盖同名用户文件；破坏性操作先确认，批量操作报告逐项结果，不将部分成功标为全部成功。
5. 文件 IO、归档和缩略图处理不得阻塞 UI 线程；进度回调节流，资源有明确释放时机。
6. 新增数据库结构采用递增版本迁移，保留现有设置、授权引用和待保存任务；不以删库解决升级问题。
7. 以下能力描述均为实现目标。开发各项前核对所用插件和 Android 官方 API，再记录选型结论；本文件不声称尚未核验的接口已可直接使用。

## 2. Phase 2A：基础相机增强

### 2.1 目标与交付物

在保留现有录制保存链路的前提下，增加设备能力感知的相机控制、录制规格选择和实际配置反馈。优先沿用 `PluginCameraDriver`，Flutter 页面不直接依赖 Android 相机会话对象。

交付物：能力模型、配置模型、应用结果模型、相机参数面板，以及对应控制器和界面测试。

### 2.2 实施任务

| 编号 | 功能 | 实现要求 | 验收标准 |
| --- | --- | --- | --- |
| P2A-01 | 能力探测 | 按镜头查询变焦范围、曝光范围和步长、对焦与补光能力、可用录制组合 | 切换镜头后重新校验；不支持与尚未探测分开表示 |
| P2A-02 | 倍率快捷键与双指变焦 | 从设备范围过滤 1x、2x、3x、5x、10x 等候选值；保留连续滑杆与复位 | 超范围倍率不出现；手势、滑杆和快捷键同步，不与销毁会话并发执行 |
| P2A-03 | 曝光补偿 | 按设备范围、步长生成滑杆值，提供复位；只有后端提供对应能力时启用 | 设置失败时恢复实际状态，不把未生效值显示为成功 |
| P2A-04 | 基础对焦与测光 | 支持可用的自动对焦、对焦锁定、预览点按对焦与测光；转换预览坐标 | 横竖屏、前摄镜像、预览裁切下点击位置正确；锁定不标为手动焦距 |
| P2A-05 | 补光灯 | 录像阶段以持续补光为主要语义；按当前镜头能力显示 | 前摄无灯时不可启用；切镜头、离页与异常释放时状态正确 |
| P2A-06 | 分辨率与 FPS | 基于可验证的录制组合生成列表，切换组合后重建会话并校验 | 不承诺 1440p、4K、60 或 120 FPS 必然可用；不把预览帧率直接当作录像能力 |
| P2A-07 | 视频码率 | 提供自动、低、标准、高及自定义；单位和允许范围明确 | 校验数值、编码器约束和录制组合；无法确认实际码率时标为请求值 |
| P2A-08 | 防抖 | 将产品选项映射到后端真实支持的模式；区分录像防抖、预览防抖和光学防抖 | 不为不存在的能力展示“增强”；不与分辨率、FPS 或镜头组合冲突 |
| P2A-09 | 状态信息 | 展示计时、音频状态、倍率、目标规格与可取得的实际配置 | 成品信息优先读实际文件；录制中文件大小不可取得时不展示虚构数值 |

高帧率是组合能力，不是独立开关。120 FPS 等模式只有在所选后端支持完整录像流程且真机成品通过检查时才开放；否则保持不可选并记录原因，不为凑齐选项重写整套相机。

录制中文件大小若只是根据目标码率计算，必须明确为估算，并计入音频及封装误差；不能用估算代替剩余空间安全检查。

### 2.3 配置与状态边界

- 将配置分成“支持的候选项”“用户请求值”“后端已接受值”“成品测量值”，避免只维护一份配置导致展示失真。
- 可热更新的参数也通过现有串行入口执行；需要重建会话的分辨率、FPS、码率、音频或镜头切换，录制中先询问停止保存。
- 重新配置成功前不覆盖最后一份可用配置；失败时尝试恢复，并显示失败原因或无法恢复状态。
- 前后镜头分别校验参数，切换后不把旧镜头的变焦上限、手动参数范围直接复用。
- 静音模式不申请麦克风权限；开启音频才进入相应权限流程，拒绝后不破坏可用的静音会话。
- 若成品未达到请求规格，提供可观察的降级结果，不只在日志中记录。

### 2.4 阶段验收

- 自动化覆盖能力过滤、参数组合冲突、重复配置请求、切镜头、参数失败回滚与横竖屏操作。
- 真机至少覆盖一台基础能力设备和一台具有较丰富录制能力的设备；缺失硬件时保留待验收项，不宣称已完成兼容。
- 对实际成品检查尺寸、旋转、音轨和帧率特征；可变帧率不以单个名义帧率字段判定为固定帧率。
- Phase 1 的录制、后台停止、指定目录保存与失败恢复测试继续通过。

## 3. Phase 2B：专业手动参数

### 3.1 先完成技术验证，再开放产品控件

本阶段增加真正的手动 ISO、曝光时间、白平衡和对焦距离，不能用曝光补偿或对焦锁定代替。

先做一个独立、可验收的技术验证任务，产出能力映射与后端选型记录：

1. 核对现有 Flutter 插件及其 Android 实现的公开能力、扩展入口和录像限制。
2. 验证能否在插件拥有的同一相机会话内应用所需参数，并读取生效或拒绝结果。
3. 若不能稳定接入，比较维护小范围插件扩展与实现独占的原生专业录像后端，评估升级维护、预览接入、编码与生命周期成本。
4. 用真机完成预览、手动参数、录像、停止和文件交付的完整验证后，再确定正式方案。

禁止通过另一个 `MethodChannel` 直接打开同一摄像头、假定它可以与 `camera` 插件并行控制。通道只能传递请求，不会自动取得现有会话的控制权。

若最终需要原生专业后端，它与普通后端必须互斥运行，并实现相同的上层 `CameraDriver` 契约；切换后端先停止保存和释放原会话。不要同时维护两套相互独立的录像恢复流程。

### 3.2 参数设计

| 编号 | 参数 | 单位与模型 | 依赖和边界 |
| --- | --- | --- | --- |
| P2B-01 | ISO | 整数感光度；自动模式独立表示 | 只在手动传感器控制已验证的镜头开放，校验实际范围 |
| P2B-02 | 快门 | 内部保存曝光时间纳秒，界面以秒或分数秒显示 | 与自动曝光、帧周期和 FPS 联动；不提供不可能的曝光组合 |
| P2B-03 | 手动对焦 | 内部采用后端明确的对焦距离单位，例如屈光度 | 固定焦点镜头禁用；不混淆光学焦距、对焦距离和数字变焦 |
| P2B-04 | 白平衡 | 自动、设备支持的场景模式、经验证的手动模式 | 手动色温需要明确转换和设备验证；不把场景枚举冒充连续色温控制 |
| P2B-05 | 自动与手动切换 | 独立保存曝光、对焦和白平衡的模式 | 切回自动时清理相冲突的手动请求，不让隐藏参数继续生效 |

默认遵循设备自动设置；手动模式是明确的用户选择。不支持的参数应隐藏或禁用并给出原因，不显示可操作但无效果的控件。

### 3.3 失败处理与验收

- 参数失败返回结构化原因，区分不支持、超范围、组合冲突、会话关闭和设备拒绝。
- 同一事务应用相互依赖的参数；如无法保证原子应用，应返回逐项生效结果，不能把混合状态描述为全部成功。
- 用真机验证自动与手动往返、极值、不同 FPS、镜头切换、进入后台、停止失败与资源释放。
- 验证不仅看控件值变化，还看可取得的结果元数据及成品表现；无可靠反馈时标记未验证。
- 验收未通过的参数不进入正式可选列表，其他普通录像功能仍应可用。

## 4. Phase 2C：拍摄预设

### 4.1 功能范围

| 编号 | 功能 | 实施要求 |
| --- | --- | --- |
| P2C-01 | 内置预设 | 先提供自动、日常、室内、运动、夜景等候选；每项参数须有可说明的意图和真机验证，不声称是适合所有手机的固定最佳参数 |
| P2C-02 | 我的预设 | 新建、命名、保存当前配置、更新、重命名与删除；覆盖和删除需确认 |
| P2C-03 | 应用预设 | 应用前针对当前镜头和录制组合校验，展示不支持项与建议调整 |
| P2C-04 | 状态反馈 | 区分已选预设与用户修改后的配置；部分应用不得仍显示为完整预设已生效 |
| P2C-05 | 持久化 | 预设独立存储、携带配置版本；保留最后一次成功配置，启动时重新核验能力 |

内置预设可以先覆盖 Phase 2A 参数，Phase 2B 完成后再增加手动字段。第一版不增加预设市场、在线下载或跨设备同步。

### 4.2 建议的数据结构

持久表建议为 `CameraPresets`，包含 `id`、`name`、`configVersion`、`configJson`、`createdAt`、`updatedAt`。内置模板与用户预设分开管理，升级内置模板不覆盖用户已保存的配置。

以下仅为配置契约示例，不是当前已存在的 API，也不是承诺设备支持的参数组合：

```json
{
  "configVersion": 1,
  "captureMode": "video",
  "quality": "fhd",
  "fps": 30,
  "videoBitrateBps": null,
  "audioEnabled": false,
  "zoomRatio": 1.0,
  "stabilizationMode": "auto",
  "exposureMode": "auto",
  "exposureCompensationEv": 0.0,
  "iso": null,
  "exposureTimeNs": null,
  "focusMode": "auto",
  "focusDistanceDiopters": null,
  "whiteBalanceMode": "auto"
}
```

规则：

- 字段单位通过名称或契约明确；在上述示例中，`videoBitrateBps: null` 表示自动码率，手动字段为 `null` 表示未指定。
- 预设不保存视频目标目录、授权 URI 或硬编码摄像头 ID；应用预设不改变当前文件夹。
- `configVersion` 与 Drift 的 `schemaVersion` 是不同概念，分别维护迁移逻辑。
- 旧配置缺失字段使用明确定义的默认值；未知的新版本拒绝应用并保留原配置，不静默丢弃字段后覆盖保存。
- 不支持项允许用户确认后按建议降级或取消；不得默默关闭音频、改变曝光模式或替换清晰度。

### 4.3 验收标准

- 重启后自定义预设仍可读取，改名不改变配置，删除不影响其他预设。
- 应用失败保留原先可用会话；录制中切预设遵循停止保存确认。
- 覆盖旧版 JSON 升级、损坏 JSON、未知版本、边界数值和不同镜头能力差异。
- 更换设备能力或摄像头后不盲目恢复过期手动值；降级行为可见且经过确认。

## 5. Phase 3A：ZIP 与系统分享

### 5.1 功能与操作入口

| 编号 | 功能 | 实施要求 | 验收标准 |
| --- | --- | --- | --- |
| P3A-01 | ZIP 压缩 | 支持单文件、文件夹及选中项；保留相对层级和空目录；默认输出当前目录 | 中文名、重名、大文件和深目录可处理；输出不会把自身递归打包 |
| P3A-02 | ZIP 解压 | 默认解压到当前目录下的新文件夹，执行前检查目标与冲突策略 | 不覆盖已有项目；损坏或不安全归档明确失败，不报告完整成功 |
| P3A-03 | 文件分享 | 视频与普通文件通过系统 Sharesheet 分享，可扩展多文件 | 接收方可读取内容和正确 MIME 类型，无接收应用时可恢复 |
| P3A-04 | 文件夹分享 | 先生成临时 ZIP，再发起系统分享 | 不将文件夹 URI 假装成普通可分享文件；准备失败时不打开空分享 |
| P3A-05 | 任务进度 | 显示准备、处理、完成、取消和失败；提供取消入口 | 总大小未知时使用不定进度，界面保持响应，取消后可再次操作 |
| P3A-06 | 临时文件治理 | 区分用户显式保存的 ZIP 和仅用于分享的缓存 ZIP | 分享返回时不立即删除接收方可能仍在读取的缓存，按生命周期策略延迟清理 |

归档核心优先选用 Android 标准库或成熟 ZIP 库，不自行实现 ZIP 格式。选型前验证流式读写、ZIP64、大于 4 GiB 的文件、中文文件名、未知长度输入、取消和错误报告；没有满足要求时明确限制，而不是生成不可用归档。

视频通常已压缩，ZIP 主要用于打包和组织，不承诺明显缩小视频体积。无压缩存储模式对大小、CRC 或预扫描的要求须在选型时验证，不能为节省少量 CPU 反复读取巨型视频。

### 5.2 SAF 与分享权限

- 读取和输出均通过已授权的文档提供方处理，不能假设外部存储存在可直接访问的绝对路径。
- 可以验证后直接分享可转授读取权限的文档 URI；接收端不兼容时，采用应用私有分享缓存与范围受限的 `FileProvider`，不开放整个私有目录。
- 单文件和多文件分享传递正确 MIME、URI、`ClipData` 及必要的临时读取授权；不额外授予写权限。
- 临时分享文件有独立标识、大小预算和清理策略；系统分享面板关闭不等于接收方已完成读取或发送。
- 目标空间可查询时预检查；不可查询时明确未知并处理写入失败，避免把“无法取得容量”当作“空间足够”。

### 5.3 解压安全与失败恢复

1. 校验归档条目名称，拒绝绝对路径、盘符、路径穿越、非法分隔表达和链接条目；不能只检查字符串是否包含 `..`。
2. 在目标文档树内逐级创建经过校验的路径段，不拼接伪文件系统路径。归档内重复路径、文件与目录同名、大小写冲突采用明确规则处理。
3. 对条目数、目录深度、累计解压字节数和异常压缩比设定可维护的安全上限；解压过程中持续计量，不信任归档头声明的大小。
4. 清单扫描与执行分开，执行时仍重新检查冲突和权限；扫描后发生的外部变更不能导致静默覆盖。
5. 所有部分产物按任务登记，取消或失败只清理本任务创建的内容；不能递归删除原有目标目录。
6. 若文档提供方不支持可靠原子重命名，则采用可见的提交状态和任务日志，不能承诺全量原子回滚。
7. 首版不支持加密 ZIP、分卷 ZIP、RAR、7z 和 tar.gz；检测到不支持格式时明确拒绝，不盲目尝试解压。

本阶段默认不增加后台服务。长任务在前台执行；后台切换采取受控中止或明确可验证的继续策略，进程终止后将未完成任务标记为中断。重试可从安全的条目边界或整项重新开始，不承诺任意压缩字节位置续传。

### 5.4 阶段验收

- 压缩后用独立解压工具核对文件数、层级、空目录及内容校验结果；大文件不得整体读入内存。
- 覆盖恶意路径、链接条目、重复条目、损坏归档、解压体积膨胀、取消、授权失效和空间不足。
- 分享至少验证系统接收端和常用第三方接收端；接收方实际能读取内容才算通过，不以 Sharesheet 弹出为成功标准。
- 失败恢复与清理测试证明不会删除原有用户文件；归档和缓存任务不阻塞当前录像的停止保存流程。

## 6. Phase 3B：文件效率工具

### 6.1 批量选择与批量操作

| 编号 | 功能 | 实施要求 | 验收标准 |
| --- | --- | --- | --- |
| P3B-01 | 批量选择 | 长按进入选择模式，支持勾选、全选、取消和数量反馈 | 返回优先退出选择模式；刷新后剔除已不存在的选中项 |
| P3B-02 | 批量删除 | 汇总去重后的影响数量并确认，逐项执行和报告 | 同时选择父子项不重复删除；失败项目仍可识别和重试 |
| P3B-03 | 批量移动 | 首版限定同一已授权根目录，目标通过目录选择界面确定 | 禁止移入自身或后代；移动成功后旧位置消失、目标完整可读 |
| P3B-04 | 批量重命名 | 支持前缀、后缀、序号与文本替换，先预览新旧名称；补齐单文件改名入口 | 默认保留文件扩展名；校验重名、长度、空名、互换名称和提供方限制 |

移动采用提供方可验证的移动能力；若不支持，回退为复制、校验、再删除源。目标提交前不得删除源；源删除失败时显示“复制完成，源未删除”，不能再次盲目复制生成重复文件。

跨根目录移动暂不纳入首版。未来开放时须单独设计双根授权、不同提供方能力、空间评估和中断恢复，不把同根移动简单放宽为任意 URI。

批量任务需有稳定的项目标识与逐项日志。重试仅处理未完成部分；源文件在执行期间被外部修改时停止该项并报告。取消表示停止尚未开始的操作及安全结束当前项，不承诺恢复已经永久删除的内容。

目录改名或移动可能改变文档 ID。操作后重新获取条目，并更新导航、选择项、缓存及相关任务引用；当前待保存录像的目录保护仍然生效。

### 6.2 搜索、排序与缩略图

| 编号 | 功能 | 实施要求 | 验收标准 |
| --- | --- | --- | --- |
| P3B-05 | 文件名搜索 | 当前目录优先，递归搜索作为显式范围；异步遍历、可取消、可分批显示 | 支持中文名称，结果注明位置；未完成扫描不显示为完整结果 |
| P3B-06 | 排序扩展 | 保留现有名称、修改时间、大小排序；增加可取得的创建时间排序 | 未知创建时间不拿修改时间冒充，未知值仍置后；当前排序不重做 |
| P3B-07 | 视频缩略图 | 按可见项惰性加载，限制并发和缓存大小，使用内容 URI 解码 | 快速滚动不显示错图；失败回退图标；删除、改名与外部修改后不使用陈旧内容 |

首版搜索采用明确的名称包含匹配，不增加全文索引、正则搜索或视频内容识别。递归访问失败应显示部分结果和失败位置，保留取消能力。

缩略图缓存键包含内容标识、可取得的修改指纹与请求尺寸。若提供方不提供可靠修改时间，应设计显式失效或有效期；不能认为 URI 不变就代表文件内容不变。

### 6.3 阶段验收

- 覆盖父子重复选择、只读文件、部分删除、移动中断、重名、循环目标和预览后发生外部改名。
- 在千级目录条目和逐级加深的目录结构上验证扫描、取消和滚动响应，并记录测试设备与数据规模。
- 不以同时扫描整个目录树、计算全部目录大小、解码所有视频作为页面进入前置步骤。
- 从搜索结果播放或进入目录后，可返回原搜索上下文；批量操作结束后选择状态与真实文件列表一致。

### 7.3 平台契约

- 命令请求携带操作 ID、明确的输入类型和参数单位；错误码稳定，用户文案可独立演进。
- 长任务采用命令调用加进度事件的边界，例如 `MethodChannel` 启动和取消、`EventChannel` 回报状态；具体名称在实现时统一定义并测试。
- 进度模型建议包含 `operationId`、`stage`、已处理项目数、已处理字节数、可空的总量和 `canCancel`；终态包含成功、失败、跳过及部分成功结果。
- 大文件数据不经平台通道传递，通道仅传 URI、标识、配置和进度。
- 相机后端是唯一会话所有者。存储操作按资源冲突控制并发，归档任务不能长期占用唯一队列导致停止录像后的保存请求饥饿。
- 所有通道补充请求校验、结果解析和异常契约测试；订阅与原生资源在页面、任务或引擎生命周期结束时释放。

### 7.4 数据库与兼容性

当前 [数据库源文件](../lib/app/database/database.dart) 为 schema v2。建议按实际交付顺序递增版本，而不是一次性创建所有未来表。

| 数据 | 建议演进 | 迁移与保留要求 |
| --- | --- | --- |
| AppSettings | 最后成功配置、预设引用及必要 UI 偏好 | 现有根 URI、音频和排序偏好不丢失；新字段提供兼容默认值 |
| CameraPresets | 在 Phase 2C 新增用户预设表与版本化 JSON | 旧配置显式升级，未知版本不覆盖原数据 |

| FileOperationJobs / Items | Phase 3 按恢复需求新增归档、移动或批量操作日志 | 记录原始目标、逐项状态和本任务创建的产物，支持幂等重试与受限清理 |

数据库迁移只修改源表定义与迁移代码，再用既有生成工具更新代码。升级测试从真实旧 schema 构建数据库，验证设置、预设和进行中任务；不手工改生成文件，也不复用 Phase 1 删除模板表的方式迁移用户数据。

| M6：ZIP 与分享 | M0，稳定的存储与任务契约 | P3A-01 至 P3A-06 | 安全解压、独立归档校验、接收端读取和取消清理通过 |

> M6 进度（2026-09-17）：自动化部分完成，真机与接收端验证待执行。交付内容：
> - 归档核心（P3A-01/02）：Kotlin `archive/` 使用 Android 标准库 `java.util.zip`（构造器显式 UTF-8；ZIP64 由库内部按需处理，Android 未暴露 `Zip64Mode` 开关），流式读写、64 KiB 缓冲、大文件不整体读入内存；压缩支持单文件与文件夹（服务层按条目列表设计，多选入口随 M7 批量选择提供），输出位于当前目录并自动避让同名文件，输出压缩包不会被递归打包；解压默认到当前目录新文件夹，扫描与执行分离、执行时重新校验路径与冲突，重复路径/文件与目录同名/大小写冲突保留首次出现并计为跳过。
> - 安全上限：条目数 5000、路径深度 32、累计解压 8 GiB、压缩比 200（仅对声明解压量超过 1 MiB 时判断）；拒绝绝对路径、盘符、路径穿越、反斜杠与空段；`java.util.zip` 不暴露 unix 模式，符号链接条目会被解为普通文件，不构成目录逃逸（已记录为库限制）。
> - 取消与清理（P3A-05/06）：取消按操作 ID 生效，失败与取消只删除本任务创建的部分压缩包/解压产物；分享缓存 ZIP 位于应用私有 `cache/share_cache`，24 小时 TTL、1 GiB 预算、5 分钟保护期，启动时清理一次。
> - 分享（P3A-03/04）：文档 URI 直接以临时读授权分享且不授予写权限；文件夹先生成缓存 ZIP 再经 `FileProvider`（`share_cache` 范围受限）分享；无接收方时返回 `no_app` 而不打开空分享；多文件按公共 MIME 处理。
> - 进度与并发（P3A-05）：MethodChannel 启动/取消 + EventChannel 进度（阶段、已处理项、可空总量、可取消），总量未知时界面使用不定进度；归档使用独立串行队列，不会阻塞录像停止保存。
> - 验证证据：Dart 95 项测试（归档模型、通道协议与进度事件、控制器委托与错误横幅、Widget 操作菜单与进度取消）、Kotlin `ArchiveRulesTest` 与既有 `StorageRulesTest` 通过、`flutter analyze` 与格式检查通过、调试 APK 构建通过。
>
> 遗留待真机验收：压缩产物用独立解压工具核对文件数/层级/空目录与内容；中文名、大文件（含超过 4 GiB 的 ZIP64）与深目录真机表现；分享在系统接收端与常用第三方接收端的实际可读性；SD 卡与只读提供方的归档失败路径；解压体积膨胀与空间不足场景。
| M7：文件效率 | M6 的任务能力；缩略图和当前目录搜索可独立实现 | P3B-01 至 P3B-08 | 批量部分失败可恢复，目录变更不破坏待保存录像 |
| M8：版本验收 | 本次计划纳入交付的里程碑 | 完整回归记录、兼容性清单、已知限制和安装包 | 功能与文档一致，无未披露的高风险数据问题 |

### 8.2 每项任务的完成定义

- 有明确入口、正常态、加载态、空态、失败态和可达的退出或取消路径。
- 外部输入、参数范围、权限与资源状态均校验，业务错误不会变成未捕获异常。
- 影响文件内容的操作有冲突策略、成功判据和失败恢复；清理行为只针对已登记的应用或任务产物。
- 已覆盖直接相关单元测试与 Widget 交互测试；涉及 Kotlin 存储或归档规则时补原生测试。
- 在规定设备上完成实际流程，截图及一次性测试产物放入项目 `.cache/`，不提交。
- 对公开契约和持久数据变化有迁移说明；需要新增依赖时记录必要性、维护来源和许可证检查结果。
- 代码审查发现的阻塞问题已修复；未解决的设备限制明确写入交付说明。

### 8.3 验证矩阵

| 范围 | 必测场景 | 通过依据 |
| --- | --- | --- |
| 相机权限 | 首次拒绝、再次进入、系统设置恢复、音频拒绝 | 不崩溃，静音可用，状态与授权一致 |
| 相机会话 | 快速连点、切镜头、旋转、后台、参数重建 | 单一会话、无重复录制、资源最终释放 |
| 保存恢复 | 停止失败、暂存失败、SAF 失败、任务重建 | 有文件时可恢复；无完整文件时不承诺可恢复 |
| 存储提供方 | 内部存储、SD 卡、只读、撤权、外部改名 | 不依赖真实路径，权限失败不会误禁用无关根目录 |
| 参数与预设 | 能力不足、极值、组合冲突、旧 JSON | 不静默错误应用，失败不覆盖最后可用配置 |
| ZIP 与分享 | 巨型文件、中文名、空目录、恶意归档、取消 | 内容一致，无目录逃逸，接收端实际可读 |
| 批量操作 | 父子选择、重名、途中失败、重试、源变化 | 不重复执行已完成项，不误删原始文件 |
| UI 与性能 | 横竖屏、长名称、字体放大、千级条目、快速滚动 | 无遮挡与溢出，操作可达，扫描与解码不阻塞 UI |
| 数据迁移 | 旧设置、预设、待保存录像和中断任务升级 | 数据保留、迁移可重复验证、无破坏性重建 |

高规格模式需要相应真机证据。没有高帧率、手动传感器或特定防抖能力的测试设备时，将该项标为“未验证并保持关闭”，不是“测试通过”。

### 8.4 验证命令与环境注意事项

当前仓库已有下列验证入口。按改动风险选择直接相关测试，功能阶段交付时再执行完整检查，不以运行应用代替测试。

```powershell
dart format --output=none --set-exit-if-changed lib test
flutter test --no-pub
flutter analyze --no-pub
```

修改 Drift 源表后，从项目根目录运行生成命令，再执行迁移测试：

```powershell
dart run build_runner build --delete-conflicting-outputs
```

上一轮本机全局 Gradle 缓存异常，通过项目 `.cache/gradle` 隔离解决。需要复用该方式时，在项目根目录执行：

```powershell
$env:GRADLE_USER_HOME = Join-Path (Get-Location) '.cache/gradle'
./android/gradlew.bat -p android :app:testDebugUnitTest --console=plain
flutter build apk --debug --no-pub
```

`--no-pub` 的前提是已按当前 `pubspec.yaml` 完成依赖解析；依赖变更后先执行 `flutter pub get`。上述命令是现有项目入口，不代表文档中未来新增的功能已经测试通过。

生成目录和依赖目录继续由工具维护，不人工读取或编辑其内容。纯规划文档修改只做结构、链接和示例检查，不执行无关 APK 构建。

### 8.5 明确不纳入与待决策项

以下不在本次剩余功能阶段的默认范围内：

- 拍照、RAW、视频剪辑、转码、专业色彩工作流和视频压缩编码。
- 云同步、账号、多端共享、网络文件系统、预设市场。
- 后台持续录像、锁屏录像和后台长任务服务。
- 跨根目录批量移动、回收站、删除撤销和全盘文件访问权限。
- 非 ZIP 归档、加密归档和分卷归档。
- 其他平台、正式签名配置、商店上架及自动部署。

正式发布前还需单独确认应用 ID、品牌资源、版本与发布签名。当前 Android 构建配置仍使用示例应用 ID 和调试签名配置，调试 APK 构建通过不等于具备正式发布条件；本规划不授权修改签名、提交代码或发布应用。

需要在相应里程碑决定、而非现在默认扩大范围的事项：专业后端选型；第一批真机测试设备；内置预设的验证样本；ZIP 库与安全上限；临时分享缓存保留策略；是否将高帧率或跨根移动纳入后续版本。
